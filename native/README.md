# questlink (native)

C++20 port of the Python Link host (`host/handshake.py`, `tools/xrsp.py`, `tools/capnp_codec.py`) as a shared library with a C API, for macOS (and a Unity native plugin later) and the Windows bench. No dependencies except libusb-1.0 on macOS/Linux; Windows uses WinUSB directly so adb keeps the ADB interface.

## Layout
- `include/questlink.h`, two layers:
  - **Session API** for the Unity package (`ql_open`, `ql_poll`, `ql_get_device_info`, `ql_get_head_pose`, `ql_submit_frame_texture`, `ql_get_render_event_func`, …; matches `unity/com.elasticsea.questlink/Runtime/Native/QuestLinkNative.cs`). `src/link_runtime.cpp` keeps one process-wide runtime: an I/O thread opens USB when the Quest appears, runs the handshake, and reopens after a drop; an encode thread encodes. The runtime outlives every `ql_session`, so the headset session survives Play-mode exits. Unity's per-Play `frame_index` is only used to drop stale or duplicate frames; `frame.index` is session-wide. Textures are copied inside the render callback (`src/texture_encoder_d3d11.cpp`: D3D11 + Media Foundation on Windows; `src/texture_encoder_metal.mm`: Metal render passes split the texture into 5 IOSurface-backed strips that go straight to the VideoToolbox strip sessions, each strip its own stream with its own SPS/PPS; under Unity the passes go on Unity's command buffer via `UnityPluginLoad`). `ql_session*` is a registry token, so events queued after `ql_close` are ignored. Hands: the host sends InputControl hands-on (topic 28) once streaming (`ql_config.hands`, default 1) and `ql_get_hands` returns 26 OpenXR joints per hand from topic 8 + the topic 9 bind skeleton (`src/hands.cpp`). Controllers and haptics return `QL_ERR_UNSUPPORTED` until decoded. Audio (`src/audio.cpp`): `ql_submit_audio` queues game audio (resampled to 48 kHz, ≤100 ms, 30 ms cushion after running dry) and an audio thread sends one 10 ms block on topic 6 every 10 ms while streaming (silence when empty; topic-26 AudioControl is in the recorded setup); `ql_read_mic` returns the Quest mic (48 kHz mono int16, newest 1 s). Env: `QL_GOP` (default 1 = all intra), `QL_MBPS` (100), `QL_LOG=1` (protocol log to stderr), `QL_AUDIO=0` (no audio thread), `QL_HANDS=0` (leave hand tracking off).
  - **Host API** (`ql_host_*`): one connection driven by the caller; used by `qlhost` and the tests. Threading rules are in the header.
- `src/`: protocol core, no I/O: `xrsp` (framing, padding, transfers, reassembly), `capnp` (schema-less codec), `session` (handshake, clock sync, setup pacing, stream seq), `frame` (EncodedSlice patching), `pose` (topic 34). Transports: `transport_winusb.cpp`, `transport_libusb.cpp`.
- `src/templates_data.cpp`: Meta's recorded PC messages, generated by `py tools/gen_native_templates.py` from `tests/fixtures/handshake/control.json` and `host/replay/meta-idr.json`. The tests fail if it drifts from the fixtures.
- `cli/qlhost.cpp`: same behaviour and env vars as `host/handshake.py`, on the C API only.
- `tests/`: byte-exact checks against the fixtures (framing, transfers, capnp by allocation order, inner headers, the full handshake replayed through the C API against Meta's USB transfers), plus the session API over a fake Quest and fake encoder (`test_runtime.cpp`).

## Build
Windows (Visual Studio 2026's bundled CMake): `native\build.ps1` (Release; builds, then runs the tests). Output in `native/build/bin/<Config>/`.

macOS (Apple clang from Xcode or the Command Line Tools; tested on macOS 26.7, arm64): `brew install cmake libusb pkg-config`, then from the repo root
```
cmake -S native -B native/build -DCMAKE_BUILD_TYPE=Release
cmake --build native/build -j
ctest --test-dir native/build --output-on-failure
```
Output in `native/build/bin/` (`qlhost`, `libquestlink.dylib`, arm64, macOS 13+; brew's `libusb-1.0.a` is linked statically so the dylib needs no Homebrew at run time). Over SSH, brew is not on the non-login `PATH`: run `eval "$(/opt/homebrew/bin/brew shellenv)"` first. Without libusb/pkg-config, CMake warns and builds `transport_none.cpp` (`ql_host_open` returns `QL_ERR_UNSUPPORTED`).

USB on macOS (`src/transport_libusb.cpp`): picks a VID `0x2833` device from `kQuestPids` whose interface 0 is class `ff`/`8a` with bulk `0x01`/`0x81` (Meta's own filter is `2833,ff,8A`), claims only that interface (adb keeps the ADB interface), one process-wide libusb context. No root and no kernel-driver detach needed (vendor-class interfaces). Unplug = read/write error → the runtime/`qlhost` reopens by polling `open_usb`; why an open failed is logged once per change on the `usb` log line (`QL_LOG=1`).

## Run (bench)
macOS: no OVRService to stop. Plug the Quest in, then `XRSP_REPLAY=host/replay/meta-idr.json QL_LOG=1 native/build/bin/qlhost 30` and select Link in the headset (the Quest only sends HELLO after that).

Windows: same as the Python host: stop OVRService first, then e.g. `set XRSP_REPLAY=host\replay\meta-idr.json` and `native\build\bin\Release\qlhost.exe 30`. At the end it prints the `XRSP_ATTACH` values for a follow-up run.

Differences from `handshake.py`: a handshake timeout exits with code 1 instead of reopening the device; replay uses the embedded EncodedSlice headers (identical to the ones in Meta's and `encode_pattern.py`'s clips); while listening without a clip it logs per-topic counts every 2 s instead of every message.
